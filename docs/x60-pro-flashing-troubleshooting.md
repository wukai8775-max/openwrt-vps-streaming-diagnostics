# RG-X60 PRO V2.00 刷机现场复盘：问题、证据与解决结果

[中文首页](../README.md) · [文件准备与校验](x60-pro-firmware-preparation.md) · [已验证的初刷步骤](x60-pro-stock-to-kwrt-v2.md)

**实机操作记录日期：2026-11-02；复盘整理日期：2026-11-04（Asia/Shanghai）。** 本页整理同一次原厂到 Kwrt 的安装过程。型号为 RG-X60 PRO、铭牌硬件 V2.00、原厂 ReyeeOS 1.226.2120；最终为 Kwrt `25.12-SNAPSHOT` revision `10.28.2026`、kernel `6.12.112`、board `ruijie,rg-x60-pro`、107 MiB UBI。

具体文件、校验值和写入命令集中在[初刷步骤](x60-pro-stock-to-kwrt-v2.md)。这里解释现场为何停下来核对、哪些现象容易误判，以及最后用什么证据确认解决。失败尝试和静态源码分析都没有被改写成通用推荐刷法。

## 1. 实际走通的安装过程

| 阶段 | 本次完成的事情 | 进入下一阶段前的证据 |
|---|---|---|
| 辨认原机 | 读回硬件、原厂版本和实际分区 | 原厂 UBI 为 63 MiB；不能由旧机同型号推定新机布局 |
| 取得管理权限 | 机主开启开发者模式，使用本人设备的原始凭据完成 SSH 认证 | 服务可达、认证成功及权限读回分别确认 |
| 备份 | 导出原厂配置，读出完整 NAND main data，并提取七个实际分区 | 完整文件与各分区都和设备端独立 SHA256 一致 |
| 调整引导 | 写入精确 FIP，并准备有效的 512 KiB 引导环境 | FIP 写后读回、环境 CRC 与字段核对；不改 BL2、Factory 等分区 |
| 先测 RAM 路径 | 启动官方 initramfs，验证后续环境清理能力 | 临时系统实际上线；匹配 ABI 的模块、环境读写与恢复测试通过 |
| 写入系统 | 在 U-Boot Web 上传 Kwrt，并在同次上传选择 `ubi-107m` | 完整长度、MD5、布局标签一致，再单次触发执行 |
| 清理临时菜单 | 再进 RAM，只删除两个临时 Web 菜单变量 | 保留 `mtd_layout_label=ubi-107m`，核对原始环境读回并卸载模块 |
| 最终验收 | 正常启动 Kwrt，再完成一次正常重启 | 版本、板型、107 MiB UBI、管理页、SSH、有线和无线接口读回通过 |

这些是本例已完成的阶段。备份恢复、原厂回退和实际直播能力有各自的验收条件，不能由安装成功推导通过。

## 2. 现场遇到的问题与处理

### 2.1 原厂升级页拒绝 Kwrt，文件根本没有上传

**现象与证据：**选择 45,947,151-byte Kwrt 文件时，原厂前端的 30 MiB（31,457,280 bytes）限制立即拒绝。这个失败发生在文件选择阶段，没有上传，也没有进入后台写入。

**本次处理与结果：**保留拒绝记录，核对前端流程后改走已确认的引导安装路径。没有改后缀、压缩或绕过限制。这个前端错误只能解释本次为什么不能使用该入口，不能证明后台支持何种第三方封装，也不能证明 Kwrt 与实机兼容。对应[原厂接入与备份](x60-pro-stock-to-kwrt-v2.md#2-取得原厂管理权限并保全原机数据)。

### 2.2 同型号旧机已经运行 Kwrt，新机仍是原厂 63 MiB 布局

**现象与证据：**原厂实机读回的 UBI 从 `0x680000` 开始、长度 `0x3f00000`，为 63 MiB；本次精确 Kwrt 镜像对应的是 107 MiB 布局。板型名称相同、文件名相同或镜像体积小于某个分区，都不足以证明布局适配。

**本次处理与结果：**先固定下载文件及 SHA256，再按实际分区和引导能力选择路径。最终由 U-Boot Web 在系统上传时指定 `ubi-107m`，并在 Kwrt 启动及重启后读回 `0x6b00000`、107 MiB UBI。没有把旧机的静态兼容记录当成新机已验证。布局解释见[63 MiB 与 107 MiB 的区别](x60-pro-firmware-preparation.md#4-63-mib-与-107-mib-的区别)。

### 2.3 开了开发者模式，网页密码仍不能登录 SSH；原厂重启后入口也会变化

**现象与证据：**开发者开关、SSH 服务返回 banner、SSH 认证成功是三个不同状态。本次网页管理凭据没有直接完成 SSH 认证。原厂重启后，先前打开的开发者 SSH 入口未保持可用；现场由机主再次恢复开发者模式，并读回开启状态。

**本次处理与结果：**使用本人设备标识在本机离线核对原始凭据，正常完成认证并读取实际权限和分区；没有添加账户、注入账户命令或猜测一组密码。来源固定提交已在[初刷步骤](x60-pro-stock-to-kwrt-v2.md#2-取得原厂管理权限并保全原机数据)说明。每次原厂重启后重新确认入口和认证，不把开发者模式当成永久恢复通道。这个观察也不代表新 Kwrt 的 SSH 会以相同方式关闭。

### 2.4 配置导出成功，还缺完整的原机备份

**现象与证据：**网页导出的配置文件不能覆盖 BL2、FIP、Factory/校准及其他原始分区。原机 NAND 的整片读出和七个分区必须另行核对，不能只对电脑上的多个副本计算同一个 hash。

**本次处理与结果：**取得 134,217,728-byte 完整读出，按设备实际 offset 提取七个分区；完整文件和每个分区都与设备端独立 SHA256 对照通过。该备份是经 ECC 校正的 **main data，不含 OOB**；运行中 UBI 的文件系统一致性和恢复过程没有验证，不能称为已测试的全片救砖镜像。

设备端的分区读取仅由已认证的 root 执行。电脑副本留在维护账户专用的私密目录；备份目录、文件和校验清单应限制为仅该账户可读写，例如目录 `0700`、文件 `0600`，创建文件前使用 `umask 077`。原始备份及配置不放在网页目录、公共共享或 GitHub 附件中。

### 2.5 FIP 已写入，为什么还需要单独处理 env

**现象与证据：**FIP 保存本次要更换的引导组件，`u-boot-env` 保存引导参数与布局选择；它们是不同的实际分区。FIP 文件校验正确，并不意味着环境变量有效或设备已经进入新的 Web 界面。

**本次处理与结果：**引导调整只涉及 FIP 和 env；没有据版本差异顺手改写 BL2、Factory、product_info 或 kdump。候选 FIP 为 834,121 bytes，实际 FIP 分区为 2 MiB；候选比较取读回的相同长度前缀，完整分区 hash 另记。随后通过新 Web 的 `/version`、实际启动结果和环境读回确认阶段变化。容量、payload 身份及源码比对只用于排除具体不匹配，未单独当成执行成功证据。对应[引导与环境步骤](x60-pro-stock-to-kwrt-v2.md#3-写入-fip并准备可用的-web-启动环境)。

### 2.6 多次按 RESET 仍未进入 Web；原 env 的 CRC 通过也不能用

**现象与证据：**本机 RESET 的 GPIO9 active-low 信号已经读到，但两次按住 RESET 断电上电都未进入 Web，仍看见原厂页面。GPIO 信号正确并不能证明这个构建的按键入口已走通。没有把按键失败直接归因为 FIP 写入失败，也没有据此确认唯一根因。

原环境还出现过 **CRC 有效、数据区主要为 FF、没有可用键值** 的状态。校验层通过只能说明 CRC 与数据相符，不能代替内容解析；盲目对它使用 `fw_setenv` 或只看退出码，会误判配置已经生效。

**本次处理与结果：**改用精确构建已核对的六个默认字段，加上 `bootmenu_default=6`、正数 `bootmenu_delay=1`，生成匹配实际非冗余 512 KiB 区域的有效环境。核对 CRC、字段、长度及写后读回后，软件菜单路径实际进入 Web，读回 U-Boot `2023.07`。离线生成器和适用限制保留在[初刷步骤](x60-pro-stock-to-kwrt-v2.md#3-写入-fip并准备可用的-web-启动环境)。这是本例实际走通的替代路径，**按 RESET 的两次失败不作为推荐操作时长或通用方法**。

### 2.7 官方 initramfs 与 sysupgrade 都是 bin，为什么不能互换

**现象与证据：**本次官方 `initramfs-kernel.bin` 用于临时 RAM 启动，Kwrt `squashfs-sysupgrade.bin` 用于写入目标系统；扩展名不能区分用途。这个 U-Boot Web 的上传字段也不同：RAM 使用 `initramfs`，系统使用 `firmware`。

**本次处理与结果：**先独立上传已校验官方 initramfs，核对 9,166,140 bytes 和完整 MD5，单次执行后读回 RAM 内核。先验证能否修改并恢复环境，再写 Kwrt。RAM 启动不是被 63 MiB 布局强制要求的启动条件；本例选择它，是为实测后续清理路径。源码会在相应条件下保存布局环境，不能笼统承诺一切 RAM 流程绝不写闪存。本次独立 RAM 上传没有提交新的布局标签。对应[RAM 系统步骤](x60-pro-stock-to-kwrt-v2.md#4-先启动官方-ram-系统实测后续环境清理能力)。

### 2.8 RAM 中 env 变成 mtd1 且只读，官方 APK 又报签名不信任

**现象与证据：**RAM 系统中 env 的 MTD 编号与原厂不同，并且默认只读。只看内核版本号相同，也不足以确定内核模块 ABI 匹配。实际准备的官方 `kmod-mtd-rw` 本地包又被当时 RAM 的 APK keyring 拒绝，错误为 `UNTRUSTED signature`。

**本次处理与结果：**这两个问题分开处理，没有把关闭签名检查当作来源认证：

1. 按名称、offset、长度和擦除块重新定位 env，确认 RAM 阶段为 mtd1，使用本例实际成功的四字段临时 `fw_env.config`。
2. 核对实际 RAM 内核及完整 ABI 目录，取得对应的官方模块包。
3. 独立验证 OpenWrt 官方 `sha256sums` 的 Ed25519 签名，再确认该精确包确在已验签清单中，下载内容 SHA256 与清单一致。
4. 只对这一份已由外部清单认证的本地包，采用已记录的 `--no-network --force-non-repository --allow-untrusted`；没有将 APK 内嵌签名另行认定为可信，也没有修改全局信任策略。
5. 临时加载模块后，实际完成环境修改、读回和恢复测试；最后卸载并确认只读状态恢复。

`mtd-rw` 会解除多个 MTD 分区的只读标志，范围不限于 env；本次实际写操作仍只针对已确认的环境区域。模块、ABI、签名认证前提、参数及配置格式见[RAM 内核与权限处理](x60-pro-stock-to-kwrt-v2.md#ram-内核mtd-编号及写权限)。不能用任意同版本包、强制加载或单纯 `allow-untrusted` 替代上述证据。

### 2.9 上传成功不是刷入成功，执行入口也不能当成轮询

**现象与证据：**U-Boot Web 的 `/upload` 暂存与检查文件；`GET /result` 会执行后续动作，并非只读状态查询。布局标签在上传阶段保存，不能仅在执行 URL 的查询参数里补上。

**本次处理与结果：**系统上传使用 `firmware` 文件字段，并在同一次上传提交 `mtd_layout=ubi-107m`。实际响应中的 **45,947,151 bytes、完整 MD5、`ubi-107m`** 三项全部核对后，仅调用一次 `/result`，不设置自动重试。MD5 这里只核对完整传输内容，来源认证沿用固定 SHA256/来源记录；响应 `success` 后仍等待新系统上线及读回。遇到响应丢失应先查看已有状态，不能盲目再触发写入。完整字段与本次响应见[系统写入步骤](x60-pro-stock-to-kwrt-v2.md#5-选择-107-mib-布局并写入-kwrt)。

### 2.10 刷完再次回到 Web，是系统没刷进去吗

**现象与证据：**本次用于进入 Web 的两个菜单变量是持久设置，写系统不会自动删除。它们还在时，设备再次启动进入 Web，并不足以判断 Kwrt 写入失败。

**本次处理与结果：**重新用官方 initramfs 启动 RAM，重新确认 env 分区并临时安装、加载匹配模块；只删除 `bootmenu_default` 和 `bootmenu_delay`，保留 `mtd_layout_label=ubi-107m`。核对删除结果、有效 CRC、默认字段、整个环境读回并卸载模块后，正常启动和最终重启都进入 Kwrt。

**没有把 env 整片清空成 FF，也没有删除布局标签。** 否则可能退回与已写系统不匹配的 63 MiB 默认布局。清理命令集中在[临时菜单清理](x60-pro-stock-to-kwrt-v2.md#6-清理临时菜单保留-107-mib-布局)。

### 2.11 Kwrt 的 shadow 是空字段，为什么实际不能空密码登录

**现象与证据：**静态解出的 rootfs 中，`/etc/shadow` 的 root 初始字段为空；实际开机的网页和 SSH 并没有因此允许空凭据。该精确镜像的 `/etc/uci-defaults/99-default-settings` 在首次启动时设置初始凭据，静态文件和初始化后的系统状态不同。

**本次处理与结果：**只读核对精确镜像的初始化脚本，再按其实际初始认证来源正常登录。没有把锐捷铭牌信息、原厂网页密码或原厂 SSH 凭据当成 Kwrt 密码，也没有循环尝试常见密码。确认成功的是开机后的真实认证，不只是镜像内容；初始口令和任何哈希不公开。后续账户管理需保留独立授权边界，不能把改管理员密码当成例行排障。对应[初始认证与验收](x60-pro-stock-to-kwrt-v2.md#7-电脑接线初始认证与最终验收)。

### 2.12 USB 网卡反复消失，维护连接影响电脑原有联网

**现象与证据：**USB 网卡曾从系统接口中消失或重新枚举；继续绑定旧接口名、旧地址或旧邻居记录会得到误导结果。原厂、U-Boot、RAM 和 Kwrt 的地址、LAN/WAN 角色也不同，接口存在不等于已接到当前系统的管理 LAN。

**本次处理与结果：**每次先确认当前实际接口和物理连接。维护有线口临时使用手动 IPv4、无网关，维护阶段关闭该有线接口的 IPv6，以保留电脑原有 Wi-Fi 联网及远程协作路径；没有给维护网卡设置抢占默认出口的网关。

在目标 Wi-Fi 和管理 LAN 实际可用后，后续管理改用已确认的 Wi-Fi 接入，按当前 DHCP、路由和管理页重新定位，不再依赖反复消失的 USB 接口。Wi-Fi 在首次启动前不能替代本次所需的有线维护路径。维护结束后按实际用途恢复电脑设置；设备地址、网络显示名称及电脑接口名都不作为跨环境固定值。对应[电脑接线注意项](x60-pro-stock-to-kwrt-v2.md#7-电脑接线初始认证与最终验收)。

## 3. 本次“完成”具体指什么

| 检查 | 本例证据与边界 |
|---|---|
| 备份文件完整性 | 完整 128 MiB main-data 与七个分区均通过设备端独立 SHA256 对照；恢复未测试、无 OOB |
| 引导与环境 | 精确 FIP 写后读回通过，有效环境实际进入 Web；RESET 入口未验证成功 |

| 正常重启 | 清理临时菜单后跨过一次正常重启，管理页、SSH、有线和无线接口读回通过 |
| 业务及失败恢复 | 后续客户端关联、出口和性能按各阶段另验；本页不认证真实手机持续直播、高峰容量、恢复或原厂回退 |

一次过早轮询曾读到旧进程响应，没有将其计为重启验收；最终结合重启后的实际运行时间和读回才确认完成。管理页能开、无线接口存在、普通请求成功，都不能直接替代手机真实开播验收。

## 4. 公开复盘与私密交接资料

本页公开硬件、版本、布局、精确公共文件和经脱敏的现象；原始分区、配置导出、原始环境、认证材料、截图及完整日志仍只保留在受保护的维护位置。交接时可使用 `original-whole-main-data.bin`、`partition-hashes.json` 等角色化文件名，具体路径与访问权限由机主私下保管。

公开前排除设备 hostname、序列号、MAC、真实管理地址、SSID、节点地址、密码、口令哈希、UUID、Cookie、token 和分享链接。公开检查工具只减少误提交，仍需人工阅读；不能把实际秘密换成看似脱敏但仍可还原的值。边界见 [SECURITY.md](../SECURITY.md)。

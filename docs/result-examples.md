# 结果怎么读：成功、部分下载与目标拒绝

## 默认演示：这是合成数据，不是你的网络

```sh
python3 tools/quick-check.py
```

默认示例的稳定事实如下；完整机器结果见 [quick-check-demo.json](../examples/quick-check-demo.json)：

| 项目 | 尝试 | 完整 | 失败 | 说明 |
|---|---:|---:|---:|---|
| HTTPS 小请求 | 3 | 3 | 0 | 三个合成 HTTP 204 响应 |
| 固定对象下载 | 2 | 1 | 1 | 第一轮完整 1 MiB；第二轮 15 秒仅收到 256 KiB |

第一轮完整对象的合成 goodput 为 **8.39 Mbps**。第二轮即使收到 HTTP 200 和部分数据，仍记为 `timeout_partial`，`task_goodput_mbps` 为 **null**。不能把该轮已下载部分算作成功速度，也不能把示例数字当成自己的实测。

离线示例的网络任务启动数为 **0**；示例中的三次响应和两次下载都没有真实发生。JSON 与中文报告来自同一个结果对象，不提供另一套选择性统计。

## 实测时，按类别决定下一步

| 结果类别 | 当前证据 | 合理的下一步 |
|---|---|---|
| `success` | 本次约定的请求完成 | 先保留基线；若实际应用仍卡，再测相同业务与负载 |
| `dns_failure` | 本次名称解析失败 | 对照当前接入的解析设置与另一个可控目标；尚不确定故障在哪台解析器 |
| `connect_failure` | TCP 连接没有建立 | 核对当前路由、目标服务与防火墙；不能仅凭它确定运营商问题 |
| `tls_failure` | TLS 协商或证书检查失败 | 核对时间、证书及目标配置；保留证书验证，不用忽略证书掩盖问题 |
| `timeout_unresolved_stage` | 请求超过预算，现有证据不足以定位 | 保存 connect/TLS/首字节/总时间，再分层采集；不要把单个超时直接当丢包率 |
| `timeout_partial` | 已有部分下载但任务未完成 | 保留失败分母，与同对象完整任务比较；不要靠延长期限宣称提速 |
| `http_rejected` | 目标返回 403 或 429 | 停止该分支，核对服务使用规则及等待要求；其他目标成功不抹掉本次拒绝 |
| `http_unexpected` | 状态与约定不同，例如重定向 | 核对测试对象/服务状态；工具不会自动跟随到另一个对象 |
| `object_size_mismatch` / `body_limit` | 对象不符或响应触及大小保护 | 停止下载分支，确认对象大小与预算 |
| `metrics_invalid` / `curl_failure` | 没有符合完成规则的指标或其他请求错误 | 保留失败；由进阶工具补证，入门报告不输出敏感 stderr |

不同类别可能来自同一个现象。例如目标拒绝请求并不说明路由器缓存有错；TLS 完成后仍可能在传输阶段超时。结论应跟随证据范围。

## 为什么“计划、尝试、失败、未开始”都要看

假设固定对象计划两次，第一次收到 429，工具停止该下载分支：应记录 **计划 2、尝试 1、完整 0、失败 1、未开始 1**。不能写成 0/2 个网络错误，也不能跳过拒绝后反复重试直到成功。这里是规则示意，不是另一次实测。

系统当前路由与强制接口是不同条件；默认报告用非敏感标记区分，但都没有验证代理节点。DNS 失败时即使启动了 curl，也不代表发出了 HTTP 请求；进程启动失败更不能算真正访问过目标。请求任务计数不是网络包计数。

## 小请求通过之后，仍有哪些未知

三次小响应不测带宽；两次小文件不能代表最高容量。自动路由不能证明 Wi-Fi 组、出口 IP、DNS 同路、透明代理或实际发送 socket。单目标失败也不能证明所有网站失败。手机直播、通话、晚高峰和并发需要按 [验收指南](acceptance-and-rollback.md) 另测。

历史中也发生过 [公共下载接口 429 与部分超时](au-expansion-2026-10-21.md)、[group-12 下载已收大部分却未按时完成](au-group-12-followup-2026-10-21.md)。这些真实记录保留成功、失败和回滚，不是通用参数处方。更多入口见 [案例索引](cases.md)。
